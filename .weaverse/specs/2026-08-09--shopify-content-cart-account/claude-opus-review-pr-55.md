## Non-blocking findings
- **Provider lifetime narrowed and now keyed** — `src/components/add-to-cart-form.tsx:237-247` mounts `ShopifyProductProvider` inside `AddToCartForm`, which is rendered as `<AddToCartForm key={colorway.id}>` at `src/app/products/[productHandle]/product-detail.tsx:172-176`. Previously the provider sat above the keyed boundary (old `ProductCartBoundary` wrapping the whole `ProductDetailView`), so it persisted across colorway switches and resynced via a new `product` prop; it now unmounts/remounts per colorway. Observable outcome is equivalent because the inner form was already keyed by `colorway.id` in the base, and a fresh mount guarantees selection matches the colorway rather than depending on the provider's prop-sync path. Any in-flight add-to-cart pending state is dropped on colorway switch — which was already true for the form's own state. Worth knowing, not a defect.
- **Type-safety erosion at the sanitizer** — `src/lib/cart/shopify-cart-server.ts:139` casts `result.data as Record<string, unknown>` and line 140 re-casts the whole result `as T`. Redaction remains runtime-enforced (`shopify-cart-server.ts:113-126`), so security is unaffected, but the compiler no longer proves the returned shape matches `CartGetResult`/`CartPostResult`. A future field rename in the pinned Hydrogen types would not surface here.
- **Boundary error class collapsed to `Error`** — `shopify-cart-server.ts:19,69,84,100,114,118,123`. Nothing in the frozen set narrows on `ShopifyCartBoundaryError`, and `handleShopifyCartRequest`'s bare `catch` (`shopify-cart.ts:128`) never distinguished causes, so no behavior change. Cost is diagnosability: `safeErrorLabel`-style logging now reports `"Error"` for contract violations (duplicate cart cookie, unsafe checkout URL) identically to transport failures.
- **Style drift in the route module** — `src/app/api/cart/route.ts:5` places the import after the segment-config exports (valid ESM, hoisted, but reads oddly), and line 7 uses an arrow expression where the repo convention is a function declaration; the explicit `Promise<Response>` return annotation was also dropped. `export { handleCart as GET, handleCart as POST }` is a well-established Next.js route-handler pattern and the module namespace still exposes both verbs.
- **Component layer now depends on Hydrogen types transitively** — `src/components/shopify-cart-view.tsx:7-8` consumes `ShopifyCartLineData`/`ShopifyMoney`, re-exported from `src/lib/cart/shopify-cart-react.tsx:19-20` as `CartLine`/`MoneyV2`. The `data boundary` guard (`tests/shopify-catalog-adapter.test.ts:1284-1308`) only rejects literal `@shopify/hydrogen` specifiers in `src/app`/`src/components`, so this passes, and the imports are type-only (erased). It does mean the component's compile-time shape is now owned by the Hydrogen package rather than a locally pinned contract — deliberate per the PR description, but the guard no longer detects it.
- **Unverifiable from the frozen set** — the exact shapes of `CartGetResult`/`CartPostResult` (`status` optionality on the error variant, whether `lines.nodes` is `CartLine[]` vs. a `CartLine | ComponentizableCartLine` union) and `ProductInput`/`ProductVariantInput` were not in scope. If `nodes` is a union, `ShopifyCartLine`'s `line: ShopifyCartLineData` prop would need widening. Flagging as a residual, not a finding.

## Contract verification
- **Exact Shopify variant IDs** — ✔ `shopify-cart-react.tsx:64` maps `id: variant.id` straight from the normalized variant seam; no ID is synthesized from handle, colorway, or option label. `selectedOrFirstAvailableVariant`/`adjacentVariants` (lines 79-80, 102) carry the same GIDs, and `merchandiseId` is still registered from provider state (`add-to-cart-form.tsx:153`). Only the declared return type changed.
- **Fail-closed live mode** — ✔ `shopify-cart.ts:34-37` throws when `readShopifyCatalogConfig` returns `null`; every failure path lands in the `catch` at line 128 returning 502 `cart_unavailable`. No fixture data is ever served as live truth.
- **Server-managed HttpOnly cart identity** — ✔ `hardenCartCookie` (`shopify-cart-server.ts:24-50`) still strips and reimposes `Path=/`, `SameSite=Lax`, `HttpOnly`, and `Secure` only in production; non-`cart=` cookies pass through untouched. The `cookieValues` fallback removal in favor of `Headers.getSetCookie()` (line 57) is a strict improvement — the old combined-string fallback could merge two `Set-Cookie` values into one string and evade the `cartCookieCount > 1` guard. The guard now throws before the response is constructed (line 68-70), and the 502 replacement headers carry no cookie.
- **Trusted buyer IP** — ✔ `readTrustedBuyerIp` (lines 7-22) unchanged: first `x-forwarded-for` entry only, `isIP()` validated, `127.0.0.1` outside production, hard throw in production. Reaches the Storefront client at `shopify-cart.ts:39-52`.
- **Identity redaction** — ✔ `sanitizeCartData` still requires a non-empty string `cart.id` then blanks it (`shopify-cart-server.ts:117-120`), over a `structuredClone`, and is applied on both the API path (`cartResultResponse`) and the server-seeded read (`readShopifyCart:94-98`).
- **Validated Shopify HTTPS checkout handoff** — ✔ `validateCheckoutUrl` (lines 76-103) is byte-for-byte unchanged: https-only, default port, no credentials, no fragment, Shopify-owned host allowlist; invoked from the sanitizer for any present `checkoutUrl`.
- **Fixture mode** — ✔ `useShopifyCartMode()` defaults to `false` via `createContext(false)` (`shopify-cart-react.tsx:33`), so `ShopifyCartRuntime`'s new `if (!enabled) return children` (line 42) is semantically identical to the removed explicit `value={false}` provider. `AddToCartForm` still routes to `DemoAddToCartForm`, and `toHydrogenProductInput` is only evaluated in the live branch of the ternary.
- **Dynamic / no-store cart behavior** — ✔ `dynamic`, `fetchCache`, and `runtime = "nodejs"` (required for `node:net`) are all retained at `route.ts:1-3`. `hardenCartResponseHeaders` sets `cache-control: private, no-store, max-age=0` and `vary: Cookie` on every cart response including the 502 path. The `Response.json` swap preserves the JSON content type (set by the static method when absent from init headers, which the hardened `Headers` never contains) and preserves multi-`Set-Cookie` emission, since the `Headers` instance is passed through unchanged.

## Test assessment
Server-boundary coverage is adequate and the security-critical assertions survive the refactor untouched (`tests/shopify-cart.test.ts:57-158` for buyer IP, cookie hardening, redaction, and checkout validation; lines 162-239 for the end-to-end cookie-seeded round trip). Specific gaps:

- **Duplicate cart-cookie fail-closed is untested.** The `cartCookieCount > 1` branch (`shopify-cart-server.ts:68-70`) is exactly the branch whose reachability changed when `cookieValues` was replaced by `getSetCookie()`. Add a case appending two `cart=` `Set-Cookie` headers and asserting `hardenCartResponseHeaders` throws, plus a mixed cart + non-cart cookie case asserting the non-cart cookie survives verbatim and the cart cookie is hardened.
- **`/api/cart` segment config and method exports are unguarded.** This PR rewrote that file into aliased re-exports, yet only `src/app/cart/page.tsx` is source-asserted (`tests/shopify-catalog-adapter.test.ts:1198-1204`). Extend that same test to read `src/app/api/cart/route.ts` and assert `dynamic = "force-dynamic"`, `fetchCache = "force-no-store"`, `runtime = "nodejs"`, and that the module namespace exposes callable `GET` and `POST`.
- **Provider placement has no automated coverage.** The repo has no DOM/React test harness (node:test only), so the `ShopifyProductProvider` relocation and the `ShopifyCartRuntime` disabled-path change rest entirely on manual QA. Not a reasonable ask to add here; noted as residual risk.
- Minor: `toHydrogenProductInput` is only asserted against `ridge-30-field-pack`, which has no non-Color option (`tests/shopify-cart.test.ts:39-55`). A `weatherline-shell` case asserting `options` order (`Color` first, then `Size`) and that `adjacentVariants` ids equal the fixture's colorway-filtered variant ids would pin the more interesting path.
